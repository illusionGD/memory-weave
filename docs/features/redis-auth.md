# Redis 登录会话

Redis 保存登录会话和来源限流，使有效登录能够跨后端热重载、普通重启和 PM2 重启继续使用。MySQL 仍保存用户、伴侣、聊天、记忆和持久任务；Qdrant 仍保存可重建的向量索引。本功能不新增 SQL 迁移。

## 登录行为

- Cookie 沿用 `memory_weave_session`，保留 HttpOnly、SameSite=Strict 和部署对应的 Secure 设置，token 不进入 JSON 响应或浏览器 localStorage。
- 登录后固定 12 小时到期。访问接口和重启均不延长有效期，不进行滑动续期。
- 同一部署的当前凭据最多有 10 个有效会话，第 11 次登录原子淘汰最早会话。多个同配置后端共用限额。
- 退出只撤销当前会话，其他终端继续登录；撤销成功后才清除 Cookie。其他同配置进程会立即拒绝已撤销的 token。
- 每个可信连接来源在 60 秒内最多尝试登录 5 次，最多保留 1024 个活跃来源；重启和换进程不能清空计数。不信任任意 `X-Forwarded-For` 来绕过该限制。
- 从原内存 Map 版本首次升级需要重新登录一次；后续重启可以继续使用尚未到期的登录。

原先每次启动生成的随机 `salt` 仅用于 scrypt 密码校验。token 查找使用 SHA-256 摘要，不使用该 salt。重启失效的真实原因是会话 Map 随进程退出而丢失，因此本次保留随机密码 salt，并将会话记录移入 Redis。

## 配置和凭据轮换

| 配置                            | 用途                                                                           |
| ------------------------------- | ------------------------------------------------------------------------------ |
| `REDIS_URL`                     | Redis 连接地址，支持 `redis://` 和 `rediss://`；只在服务端使用                 |
| `REDIS_NAMESPACE`               | 稳定的部署隔离前缀，同一部署所有进程必须一致；开发、测试、生产分别设置         |
| `AUTH_SESSION_SECRET`           | 稳定的 64 位小写十六进制随机密钥，由 setup 首次生成，不随重启或再次 setup 改变 |
| `REDIS_PASSWORD` / `REDIS_PORT` | Compose 认证和端口配置，默认仅绑定本机回环地址                                 |
| `TEST_REDIS_URL`                | 验证专用 Redis，测试额外生成独立随机前缀并在结束后清理                         |

Redis 会话 key 使用 token 摘要，不保存原始 Cookie。会话范围包含由稳定密钥和部署密码计算的 HMAC 版本，不保存明文密码或裸密码摘要。修改登录密码或 `AUTH_SESSION_SECRET` 后，切换到新配置的进程不再接受旧会话；旧记录按剩余 TTL 自动过期。

轮换时必须让所有后端进程加载同一份新配置，并停掉仍使用旧配置的进程。若将密码与密钥同时回滚为旧值，旧版本的未过期 Cookie 可能重新匹配。因此，要彻底撤销旧登录，或恢复旧 Redis 备份后重新建立认证状态，应生成新的 `AUTH_SESSION_SECRET`，更新所有进程，之后不再回滚到旧密钥。

`REDIS_NAMESPACE` 允许 1 到 96 位字母、数字、冒号、下划线或连字符，并以字母或数字开头。不允许 glob 字符。命名空间用于隔离 key，不能替代独立 Redis 账号、访问控制或网络隔离。

## 失败和恢复

Redis 连接或操作失败时，登录和需要校验现有 Cookie 的请求返回 HTTP 503、`code: 50303`，文案为“认证服务暂时不可用，请稍后重试。”。不会自动回退进程内 Map，不会将有效性未知误报为密码错误，也不会清除现有 Cookie。

Redis 恢复后，下次请求重新连接；尚未到期的原会话可以继续使用。token 缺失、格式错误或经 Redis 确认不存在时仍返回原有 401。退出操作响应不确定时不自动重放，客户端也不应将其显示为退出成功。

连接及认证握手最多等待 1.5 秒，单次命令最多等待 1.5 秒，关闭无限离线排队和自动写操作重试。应用退出仅关闭 Redis 连接和清理内存密码哈希，不删除 Redis 会话或限流记录。

公开 `/api/health/live` 只报告进程存活；`/api/health/ready` 将 Redis 纳入依赖检查。已登录的系统状态响应包含 `authenticationStore: { engine: 'redis', status: 'connected' }`；状态和错误响应不返回连接串、密钥或 Cookie。

## 部署与本地使用

先在项目根目录运行 `pnpm setup` 补齐稳定配置。通过 Compose 使用 Redis 时运行：

```bash
docker compose --env-file .env -f deploy/compose.yaml up -d --wait redis
```

已安装 Redis 时将 `REDIS_URL` 指向该实例即可，MySQL 可以继续使用原来的本机安装方式。云服务器上的 Redis 仅供后端访问，不直接暴露公网；远程受管 Redis 使用供应商提供的认证和 TLS 配置。启动配置及 PM2 使用约定见 [README](../../README.md)；本轮未提供完整 PM2 部署配置，也未部署到用户云服务器。

Compose 使用独立的 Redis 数据卷和 AOF，每秒落盘。普通后端重启不会影响 Redis；保留数据卷重建 Redis 容器可以恢复已有会话和剩余 TTL。突然掉电可能丢失最近一秒的创建或撤销记录，恢复旧备份也可能缺少最新撤销信息；需要保证旧登录全部失效时按上文轮换会话密钥。

## 验证方式

认证测试通过实际 HTTP 和真实 Redis 验证，不 mock 认证服务或改写 Redis 内部 key 来模拟成功。覆盖跨应用重建、多个应用共享与退出、并发十会话上限、固定到期不续期、共享限流、密码及密钥轮换、部署隔离，以及真实 TCP 断线和无响应握手的 503 与恢复行为。12 小时 Cookie 属性单独断言；实际过期采用程序化测试配置缩短时长，部署入口仍固定使用 12 小时。

后端测试、测试子进程和浏览器验收分别生成独立前缀；重启测试明确复用同一前缀。清理仅扫描并删除本轮前缀，不使用 `FLUSHDB` 或 `FLUSHALL`。

部署验收还覆盖 setup 重复运行保留既有值、不输出凭据、特殊字符密码 URL 编码、Redis 匿名访问被拒绝，以及保留卷重建后测试 key 与递减 TTL 保持。Node 22.23.4 下全工程格式、lint、类型检查和生产构建通过。真实依赖后端全量 22 文件、194 条中，193 条通过，另 1 条旧“重启后 401”测试按新行为修正；随后认证与伴侣两套 29 条全部通过，未跳过测试，最终修正仅涉及旧断言。桌面/手机浏览器 30 条通过，包含两端 503 后保留 Cookie 并重试恢复。

`pnpm deploy --prod` 和完整 Docker 镜像构建均通过。原生 Node 与非 root 生产容器均验证了两端静态入口、真实 MySQL/Qdrant/Redis 就绪、登录后重启继续使用原 Cookie、退出后旧 Cookie 返回 401。验证使用独立临时数据库和 Redis 前缀，完成后清理；未部署到用户云服务器。
