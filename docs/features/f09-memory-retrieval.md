# F09：把记忆接入聊天

比较基线：`0d5d4c0`（F08）。普通聊天也会检索，不要求问句。每轮将有来源的相关记忆与尚未整理的新原文一起交给聊天模型，并保存实际输入来源；初始人生与人格保持原有版本规则。完整记忆管理按 F10，自主反思与成长按 F15。

## 启动与验收

已有 MySQL、Qdrant 可继续使用，在项目根目录执行：

```bash
git pull --ff-only origin dev
pnpm install --frozen-lockfile
pnpm db:migrate
pnpm dev
```

本版只追加 `0007_memory_retrieval`，不修改已发布的 0000–0006。Docker 完整部署执行 `docker compose --env-file .env -f deploy/compose.yaml up -d --build --wait`，保留现有数据卷。

1. 对同一伴侣开启两场私聊。在第一场补充新地址，立即在第二场说「寄东西用新地址就好」。
2. 展开回复下方「本轮参考的记忆与新消息」，查看实际选入的原文、记忆、历史标识及来源入口。刷新后保留同一轮快照。
3. 真实 memory 模型整理出条目后，后续聊天同时使用相关条目和待整理补充；旧地址不会因向量索引尚未更新而成为唯一材料。
4. B 的私聊不能查询 A 的私聊；群聊只能取得本会话材料。跨会话首版限于同一用户、同一伴侣、同一运行代次的私聊。
5. 删除来源会暂时限制可能引用它的同伴侣私聊；清理完成后独立原文仍在，依赖该来源的回复和记忆失效。

```bash
pnpm verify:f09
```

脚本保留两位验收伴侣及会话，只使用 test 角色，不改配置或删除已有数据。它检查普通陈述补读、实例隔离、实际聊天上下文、刷新与初始人生不变。自定义整理间隔极短时，应在隔离部署关闭自动整理后验收“尚未整理”场景；脚本不会替部署者改参数。

默认 test 聊天仍输出固定文字，memory 返回空候选，embedding 的测试编码不用于语义检索。网页看到来源代表链路生效，不代表模型已经理解内容。真实理解需要配置 chat、memory、embedding 供应商、模型及价格，步骤沿 F03。生成文字如何利用来源由聊天模型决定；程序保证来源、版本和权限，不能保证语义百分之百正确。

## 查询与预算

每次先确定实例、代次、会话及可见范围。聊天保留原始输入，最多取三条前文的末尾 512 字符辅助指代；不调用额外大模型编造查询实体。显式过去经历词触发历史模式，故事词触发虚构模式；这是有限规则，复杂指代与隐含时间仍需真实模型评估。公开接口可以传明确对象、故事、记忆 ID 和历史模式。

- 直接路径：按记忆身份、对象、现实/故事和当前版本条件查询；从有限近期版本补查词项，时间近本身不作为相关依据。
- 词法路径：版本化 `Intl.Segmenter('zh')` 中文分词与中文二元片段倒排表，覆盖已有姓名、别名与地址。不会自动创造未提供的别名。
- 向量路径：只在当前空间已有索引时编码查询；Qdrant 带归属、实例、代次、会话、空间过滤，默认精确查询；显式启用 ANN 后候选不足时再做一次有限精确查询。简单应答跳过向量调用。
- 融合：按排名做 RRF，按版本去重，随后在 MySQL 复核当前头、失效状态及全部原文来源。普通模式只给当前版本；历史模式明确保留旧版本、纠错及分歧标记。历史向量不保留，历史回忆使用直接/词法路径。
- 新补充：逐实例查询尚未 processed 的确切原文范围，与索引无关。优先选最新完整消息，超过条数或字符预算明确标记 `pendingComplete=false`，不会截断后声称整条已读。

同一空间最多枚举 200 个授权会话参与向量过滤，溢出标记候选受限；数据库补读仍按可见范围进行。当前任务输入先保留本轮必要交流，再按预算省略旧聊天、低排名记忆与较早补读，省略会传给模型和网页。没命中不等于从未发生；有缺口时模型应保留不确定性。

`.env` 的 `RETRIEVAL_CONFIG_JSON` 由 dev、start、Compose 共用，修改后重启：

| 参数                                | 默认值     | 作用                                          |
| ----------------------------------- | ---------- | --------------------------------------------- |
| vectorEnabled                       | true       | 是否启用真实向量索引与查询                    |
| indexBatchSize                      | 4          | 单次索引调度上限，待执行队列有界              |
| vectorTimeoutMs                     | 1500       | 每次 Qdrant HTTP 请求超时                     |
| vectorMinScore                      | 0.3        | 余弦候选最低门槛，须按实际模型校准            |
| pendingMessages / pendingCharacters | 24 / 12000 | 新原文条数与字符预算                          |
| candidates / results                | 30 / 8     | 每路候选与最终条数；历史候选最多两倍          |
| memoryCharacters                    | 8000       | 记忆正文字符预算，仍受聊天整体 token 上限限制 |
| rrfK                                | 60         | 排名融合常数                                  |

Qdrant 超时仅限制该次 HTTP；查询 embedding 另受统一模型角色超时、预算和并发约束。索引与整理共用一个后台任务位置，聊天使用普通位置，清理另有一个位置；所有模型仍受 F03 全局限额。Qdrant 不可用时可用词法、新原文继续聊天，覆盖状态明确退化；故障不会把记忆标为整理失败。

## 索引、切换与恢复

MySQL 保存权威记忆及来源。记忆提交时同事务登记 `memory_search_documents` 与词项，worker 再登记 `memory_vector_indexes` 和持久任务；外部请求均在事务外执行。Qdrant payload 只存身份与过滤字段，不存原文。点 ID 固定为记忆版本 UUID，`wait=true` 确认写入，重试覆盖同一点。

编码空间由供应商/端点、模型、维度、prompt/schema/预处理版本及编码格式共同确定；不同空间使用不同 collection，不混查，也不覆盖人格。更换配置后补建当前版本的新空间，期间仍可用数据库路径；旧空间保留以供诊断。正式构建校验、切换、回退和旧空间回收管理按 F21，本版没有完整蓝绿切换界面。

成功 embedding 结果有持久请求身份，进程恢复或显式重建复用已保存结果；Qdrant 故障有限重试后保留失败任务。显式重试创建新任务并保留旧记录；运行中或结果未知的模型调用不能换键补发。collection 丢失可逐条重建已有版本，首次重建会恢复 collection 与过滤索引。大规模批量重建管理后续完善。

聊天新轮次使用 `chat-v2`，已有固定 `chat-v1` 输入继续按旧定义恢复。MySQL JSON 重排字段不能改变恢复时的输入字节；检索快照按固定 schema 重建字段顺序。恢复不重新抽取记忆，不混入新原文。未知结果继续按 F03/F04 阻塞，不能重复发送。

## 删除与来源

`chat_memory_sources` 记录回复实际使用的记忆版本，`chat_run_sources` 记录新原文与查询前文身份；`memory_original_sources` 保留不含正文的原文身份关系，实例重置后仍能处理“后来删除旧原文”。新迁移从 F08 证据补齐旧身份关系。

生命周期协议 v3 保留 v1/v2 的旧阶段编号，新增来源传播、词项清理和外部向量确认。删除沿原文→记忆版本→版本依赖→回复继续传播。为封住传播期间的窗口，命令事务先限制该伴侣可能引用来源的私聊，完成后统一解除；这是保守范围，可能短暂限制尚未实际引用的私聊。

Qdrant 删除成功后才完成对应清理阶段；失败保留受限状态和恢复入口。读取、派发、片段发布与最终提交仍查 MySQL，迟到的向量不能变成有效内容。失效点身份每分钟有界复查，补偿外部未知迟到写入。清理正文与索引时保留无正文的来源身份和全局计量。

## 公共接口

仍返回共享的数字 `{code,data,message}`：

| 接口                                                     | 入参/用途                                                                                                              |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| POST `/api/companions/:id/recall`                        | `{requestId,runtimeEpoch,conversationId,query}`；可选 context、subject、subjectName、mode、memoryId、reality、storyKey |
| GET `/api/companions/:id/recall/indexes`                 | `runtimeEpoch`，可选 afterId；每页 50 条，返回当前空间及索引身份状态                                                   |
| POST `/api/companions/:id/recall/indexes/:indexId/retry` | `{requestId,runtimeEpoch,conversationId}`；已知失败重试或成功点重建                                                    |

检索响应包含 `memories`、`pending` 与 `coverage`。查询是按当前数据库状态执行，requestId 用于外部模型调用幂等，不承诺 HTTP 重放旧检索结果。聊天轮次另外固定实际采用的快照。证据与完整原文沿 F08/F02 接口回查。

## 评估与范围

固定中文样例见 [f09-corpus.json](../../evaluations/retrieval/f09-corpus.json)，工程验收记录及索引容量实验见 [F09 评估记录](../../evaluations/retrieval/f09-results.md)。最低门槛：人工标注基础样例命中全部期望证据；实例/故事越界、当前查询返回旧版本均为零；删除、未知结果、预算与恢复必须通过。

真实 embedding 的召回门槛、查询改写、重排、复杂时间关联与回答质量尚未评估；未配置真实供应商时不宣称语义效果达标。合成向量实验只测索引，不能替代含 MySQL、来源回查和模型延迟的全链路容量验证，也不能据此保证 2 核 4 GB 的生产容量。
