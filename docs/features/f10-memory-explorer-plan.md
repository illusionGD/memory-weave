## 1. 要解决什么问题

现在可以按某段私聊查看记忆、版本、精确引文和整理批次，也可以在聊天回复中查看本轮提供给模型的来源。缺少的是：选定一个伴侣后集中浏览其记忆，筛选关心的内容，按时间看认识如何变化，沿关系找到某条认识的依据。

建议示例：用户先说“我住杭州”，后来改为“我搬到苏州了”。后台可以看见当前地址、旧版本、对应原文和变化时间；若用户说的是“之前说错了”，则显示纠错。图谱上的“修订”“纠错”“分歧”“来源”分别说明真实保存的关系。

该功能是查看和追溯的入口。伴侣的自动整理继续运行，不增加逐条人工审批。

## 3. 页面与操作方案

管理端 `apps/admin` 的「记忆记录」升级为按伴侣浏览。推荐布局：顶部伴侣与筛选栏，下方「列表 / 时间线 / 关系图谱」切换，选择条目后打开详情面板。桌面使用表格和侧面详情，手机改为单列卡片与独立详情区；沿用后台风格。

1. 选伴侣后，默认看当前人生阶段内、用户与该伴侣的有效私聊记忆；可以缩小到某段私聊。当前支持的其他会话仍按单会话查看，不将群聊与私聊自动混合。
2. 按关键词、类型、当前状态、现实/创作范围及故事标识筛选。关键词表示文字匹配，不宣称语义检索；时间筛选明确对应“记下时间”。
3. 列表优先显示当前版本；历史版本在详情和时间线明确标注。来源失效时显示可公开的无正文状态，不回退展示旧事实。
4. 时间线展示记忆形成、变化、纠错与分歧记录；同一记忆的版本可相互跳转。它不是全部聊天原文的消息时间线，也不将缺少业务记录的操作补写成事件。
5. 图谱从当前选中的记忆或版本展开；点击原文节点查看引文和完整来源，点击旧版本查看修订历史。图谱提供图例、缩放、重置、逐步展开及等价的关系列表。
6. 原有整理批次、失败原因和已知失败重试入口继续可用。聊天端保留轻量的只读记忆与来源页面；完整管理功能归后台。

## 4. 技术方案与数据含义

### 4.1 沿用已有数据

MySQL 继续保存权威记录。复用 `memory_entries`、`memory_versions`、`memory_evidence`、`memory_dependencies` 和原文/成员可见性信息。Qdrant 不参与后台列表排序或图谱连线；本功能的浏览行为不发起模型调用，不修改人格、整理结果或模型配置。

当前 `MemoryQuery` 必填 `conversationId`，现有接口按 UUID 分页，不能直接当作跨私聊时间线。建议增加独立的记忆浏览查询契约和服务，保留原聊天端查询接口的含义。

建议新增公开只读接口，路径在契约实现时统一核对路由冲突：

| 建议接口                                           | 用途                                       |
| -------------------------------------------------- | ------------------------------------------ |
| `GET /api/companions/:id/memory-explorer/entries`  | 按范围、类型、状态、文字与时间筛选当前记忆 |
| `GET /api/companions/:id/memory-explorer/timeline` | 按记下时间返回版本事件及继续读取游标       |
| `GET /api/companions/:id/memory-explorer/graph`    | 按中心节点返回一批可见关系与继续展开游标   |

每次请求固定 `runtimeEpoch` 和查询范围。条目携带原会话身份，详情、证据和完整原文继续通过现有公共接口读取。契约维护于 `packages/contracts`，客户端维护于 `packages/browser-client`，返回统一数字 `code` 的 `{ code, data, message }`。

### 4.2 时间不能混为一谈

- **记下时间**：现有 `learnedAt` 来自该版本的创建时间，可精确排序；它不等于事件发生时间，也不等于最早原文的接收时间。
- **原文接收/发布时间**：在来源详情按实际字段展示，不改称经历时间。
- **经历时间与适用时间**：保留 `eventTime`、`validFrom`、`validUntil` 的原有精度。空值显示未知，“去年”等描述照实展示；推荐方案不为排序额外调用模型推算。
- 时间线使用 `(createdAt, versionId)` 等稳定复合游标，保持同一时间内顺序确定。固定本次浏览的时间上界，刷新才能纳入之后产生的记录；删除/权限检查始终使用最新状态，不能借快照继续展示已删除内容。

### 4.3 图谱展示实际记录

基础节点为记忆、语义版本、来源消息；基础关系为来源引用、旧版本依赖及明确记录的变化/纠错/分歧。通用依赖只能标成“依赖”，不能自动解释成“支持”或“导致”。

对象信息可作为辅助标签；用户和当前伴侣有稳定身份。其他人的姓名暂不作为跨记忆唯一身份，不能把两个“小王”自动合成一人。后续反思、活动和人格成长记录在对应功能实现后再接入图谱。

需要分别表达两种含义：

- **关系有记录**：系统确实保存了该版本引用某条消息或修订某个旧版本，不等于消息主张已经被证实。
- **内容认识来源**：现有 `epistemic` 的陈述、转述、推测、创作设定分别显示。推测内容明确标记，不用相似向量距离制造因果关系或置信度。

前端沿用总体计划中的 Cytoscape.js 方向，按图谱页面懒加载。具体版本、许可、类型适配及移动端交互在实现时核验并锁定；当前没有安装新依赖，也没有宣称完成兼容或性能验证。

### 4.4 查询与展开保持有界

建议列表/时间线默认每页 20 条，最多 50 条；图谱每次最多 50 个节点、100 条边，单页面累计最多 200 个节点，达到上限提示收起或重新选择中心。节点和边分别去重，返回是否还有下一批，不将局部图称为完整图。

这些是待实现验证的初始参数，集中维护，避免散落在各页面；不作为已测容量承诺。数据库查询使用索引、游标和有限批量校验，不将所有历史加载进应用后分页，也不为隐藏条目泄露计数。查询计划若证明现有索引不足，追加迁移，不改写已发布的 `0000–0008`。

每个节点、关系和来源都重新核对用户、伴侣、代次、成员范围和生命周期限制。切换伴侣/范围时清空旧视图，丢弃迟到请求；重置、删除或来源变化时沿用内容版本通知并补齐必要的有界状态检查，关闭旧详情和清除图谱缓存。

## 6. 用户如何验收

1. 在隔离验收数据中为同一个伴侣建立两段私聊，形成地址、偏好和创作设定记忆；在后台选伴侣查看，再按会话/类别缩小范围。另一个伴侣的记忆不出现。
2. 查看地址的当前结果和旧版本，点开引文与原文；分别验证真实变化、纠错和仍保留的分歧。
3. 切换时间线，查看记下时间与经历时间的区分；连续翻页不重复，不把模糊时间变成精确日期。
4. 从一条记忆进入图谱，展开来源及修订，查看推测标记；手机可使用同样的来源入口和关系列表。
5. 通过现有生命周期功能删除测试来源或重置测试实例；确认已打开的视图清除失效正文，刷新与重启后也不恢复。

用确定性模型 fixture 生成隔离验收记录，不直接灌业务表，也不写入真实伴侣的成长数据。默认 test 模式仍可不产生记忆；没有数据时显示真实空状态。测试通过只证明查询、展示和隔离行为，不证明真实模型提取质量。

## 7. 交付边界与风险

- 不在本方案中实现 F14 关系情绪、F15 反思、F16 成长或 F21 淡忘/embedding 切换；图谱待相应数据存在后继续扩充。
- 首轮确定为只读浏览。人工纠正、固定等总目标保留在 M12 后续管理范围；若后续调整为本次加入，先补独立任务和验收。
- 查询可能涉及多个来源校验，需测 SQL 计划与实际延迟；明确记录测试规模、P50/P95 和资源，不用空库或前端节点上限代替性能结论。
- 不改变原有记忆正文、人格和来源的持久含义。升级如只添加索引仍须记录迁移结果；没有迁移时明确说明，保留旧数据验证可读。
- 实现完成后将稳定行为、启动方式和验收结果写入 `docs/features/f10-memory-explorer.md` 与 `docs/progress.md`，按 `to-tickets` 清理本临时计划；讨论过程通过 Git 历史保留。
