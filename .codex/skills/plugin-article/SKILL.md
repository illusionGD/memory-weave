# 掘金体插件技术文（写作技能）

## 何时用

用户要写 **中文技术向推文**（掘金 / 个人博客 / GitHub 置顶长文），尤其是 **Vite 插件、工具库、npm 包** 的「从需求到实现」叙事，而不是纯 API 文档。

## 固定章节顺序（勿打乱）

按此顺序组织全文，标题可用 `##` 或一级 `#` 随平台：

1. **前言** — 场景引入：怎么遇到痛点、社区有没有现成方案、为什么自己写（可一句自嘲）。可点题 **姊妹篇**（同作者另一仓库）形成系列感。
2. **仓库** — GitHub 链接一行；npm 安装命令一行（若有 peer 依赖写清楚「别忘了装 xxx」）。
3. **需求** — 无序列表，每条短句，**用户/PM 能听懂**；技术细节放到后面。
4. **技术栈** — 核心依赖 3～6 条（库名 + 一句话职责）。
5. **实现思路** — 必拆两小节（与参考文一致）：
   - **生产环境**：`generateBundle` / 产物改写 / 路径替换策略；说明「为什么不用 AST」若适用；**关键坑**用一两句点出（如 Rolldown、MIME、`?url`）。
   - **开发环境**：`configureServer` / 中间件；**缓存**若有则单独一小段（key 因子、目录）。
6. **效果** — 可写「开发 / 生产各一张图」占位；无图则一句「克隆仓库运行 xxx」代替。
7. **总结** — 3～5 条 bullet：维护态度、Issue 欢迎、**代码仅供参考**类免责一句。

## 语气与幽默（可选）

- **默认**：口语、短句、第一人称「我」；适度 **👀 / 😂** 即可，不要堆表情。
- **幽默**：自嘲排期、ffmpeg 烧 CPU、npm 401、和产品经理对话——**不黑具体个人/公司**。
- **姊妹篇**：同系列插件用超链接点名，一句「图片卷完了轮到耳朵」类对仗可以，**勿虚构不存在的仓库链接**。

## 代码块策略

- **推流文**：贴 **骨架代码**（钩子名 + 注释 `// …`）即可，**不要**整文件大段粘贴。
- **与 README 区分**：README 求全；文章求 **故事线 + 1～2 个最亮实现点**。

## 禁止与注意

- 不编造未在仓库/README 里出现的 **API、配置项、性能数据**。
- 外链：**GitHub / npm / 掘金已发文章** 用完整 URL；掘金私有图床链接易过期，**优先让读者看仓库或本地跑示例**。
- 标题党可轻微，**不要**与正文技术事实矛盾。

## 成稿自检（复制即用）

- [ ] 七章顺序齐全  
- [ ] 仓库与安装命令可点击/可复制  
- [ ] 生产 / 开发两块都有  
- [ ] 至少一处「坑或权衡」  
- [ ] 总结含维护与反馈渠道
