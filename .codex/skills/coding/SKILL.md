# 功能开发

## 目标

将已确认的功能计划落实为可维护、可验证的代码，并确保实现范围、项目规范、测试结果和进度记录保持一致。

## 开发前

开始修改前：

- 阅读用户需求、相关 plan/tickets、仓库说明、适用 rules 和目标模块代码。
- 确认功能范围、验收标准、技术方案、依赖关系和受影响文件。
- 检查工作区现有改动，只修改当前任务相关内容，不覆盖用户已有改动。
- 如果需求、方案或验收标准存在会影响实现的冲突，先向用户提问；可合理推断的内容标注假设后继续。

## 实现流程

1. 按依赖顺序实现，优先完成能验证核心流程的最小范围。
2. 遵循仓库已有目录、命名、类型、组件、状态管理、样式和错误处理规范；适用时阅读并执行 `rules`。
3. 保持单一职责，优先复用已有模块，避免无关重构和提前抽象。
4. 外部输入、异步流程和失败场景必须有明确的类型收窄、错误处理和用户反馈。
5. 修改前后检查调用方、类型定义、接口契约、权限和兼容性，避免只修表面代码。
6. 每完成一个独立任务就进行对应的格式化、静态检查和测试，不把问题堆到最后。

## 验证

根据项目已有命令执行最相关的检查，通常包括：

- 格式化和 lint。
- 类型检查。
- 单元测试、组件测试或集成测试。
- 关键用户流程的手动验证或构建验证。

先验证改动范围，再运行必要的完整检查。失败时定位并修复由本次改动引起的问题；无法修复时记录复现命令、错误原因和影响，不得声称验证通过。不要为了通过检查而删除或弱化有效测试。

## 进度与交付

如果项目有 `progress.md` 或其他进度文档，完成任务后同步：已完成、未完成、当前阻塞和验证结果。计划文档中的任务应在真正完成并验证后再勾选。

最终回复简要说明：

- 实现了什么以及涉及的主要文件。
- 执行了哪些验证及其结果。
- 尚未完成的事项、已知风险或需要用户确认的决策。

如果任务属于较大的阶段性功能，完成当前阶段后暂停并交给用户 review，不擅自扩展到下一阶段。

## 边界

- 方案未知或存在多个重大选项时，先使用 `research`。
- 项目启动阶段的整体路线和里程碑使用 `project-plan`。
- 已确定功能的任务拆分使用 `to-tickets`。
- 本 skill 负责实际代码实现和验证，不代替需求决策。

## 检查清单

- [ ] 已阅读需求、计划、相关代码和适用项目规范。
- [ ] 已确认范围、依赖、验收标准和受影响模块。
- [ ] 没有覆盖用户已有改动或引入无关重构。
- [ ] 核心流程、异常场景和边界条件已处理。
- [ ] 已执行必要的格式化、lint、类型检查和测试。
- [ ] 进度文档和计划状态与实际完成情况一致。
- [ ] 最终说明包含改动内容、验证结果和遗留问题。
