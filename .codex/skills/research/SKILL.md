# 大功能方案调研

## 目标

在实现较大功能前，了解现有方案及其取舍，为技术选型、架构设计和开发排期提供依据，避免只罗列产品名称。

## 工作流程

### 1. 明确问题

从需求和仓库上下文中提炼：

- 用户场景、核心需求和非目标。
- 平台、部署、数据安全、预算、团队技术栈、规模和上线时间等约束。
- 当前项目已有能力、可复用模块和集成边界。
- 评估维度及优先级。未指定时，默认关注需求覆盖、集成复杂度、可靠性、长期成本、扩展性和交付速度。

缺少关键信息时做最小合理假设，并在结论中标注。

### 2. 搜集候选

根据场景选择 3–6 个有代表性的方案，尽量覆盖：

- 托管产品或 SaaS。
- 成熟的开源项目或商业 SDK。
- 基于当前技术栈自研。
- 暂不引入或延后建设的基线方案。

优先查阅官方文档、定价、许可证、发布记录、源码和可验证案例；其次参考社区资料。外部检索不可用时，说明信息范围和时效限制。

每个候选至少确认：核心能力、接入方式、成熟度、适用规模、版本或更新时间、成本、许可证、安全边界、迁移出口、已知限制和集成工作量。

### 3. 统一对比

使用相同维度比较所有候选：

| 维度 | 关注点 |
| --- | --- |
| 需求覆盖 | 是否满足必需能力，哪些需求需要定制？ |
| 集成成本 | 对当前项目的改动、依赖和交付复杂度？ |
| 成熟度 | 稳定性、更新频率、社区或厂商支持？ |
| 性能规模 | 延迟、吞吐、并发、数据量和资源消耗？ |
| 总成本 | 许可、订阅、基础设施、开发、运维和迁移成本？ |
| 安全合规 | 数据边界、权限、审计、隐私和合规能力？ |
| 扩展与退出 | 定制能力、供应商锁定和迁移路径？ |
| 开发体验 | 文档、类型支持、调试、测试和上手成本？ |

重要判断应附来源和访问日期，并区分：

- `事实`：资料直接说明的内容。
- `推断`：结合项目约束得出的判断。
- `待验证`：需要 PoC、压测、安全评审或商务确认的内容。

不要编造性能、价格、案例或兼容性数据。资料冲突时说明来源和差异，优先采用更新、权威、可复现的证据。

### 4. 给出决策

结论至少说明：

- 首选方案、适用前提和关键理由。
- 方案的主要取舍，以及不选其他候选的原因。
- 风险、未知项、验证方式和备选方案。
- 对 PoC、分阶段交付、架构设计和开发排期的影响。

必要时使用加权评分，但每个分数都要能解释。没有明显赢家时，给出条件式结论，例如低成本选 A、强合规选 B、最大可控性选 C。

## 默认输出

用中文输出简洁、可执行的调研结论，通常包括：

1. 摘要和推荐结论。
2. 背景、范围、约束和假设。
3. 候选方案及筛选理由。
4. 统一维度对比表。
5. 证据、来源链接和访问日期。
6. 成本、风险、锁定和迁移分析。
7. 推荐方案、备选方案、待验证问题和下一步计划。

仓库已有文档约定时，遵循其位置；否则可将完整报告保存到 `docs/research/<topic>.md`，并在完成后告知用户文件位置。

## 检查清单

- [ ] 已明确需求、约束、非目标和评估标准。
- [ ] 已比较多个有代表性的替代方案。
- [ ] 所有候选使用相同维度比较。
- [ ] 关键事实有可靠来源，并区分事实、推断和待验证项。
- [ ] 已考虑成本、安全、锁定、迁移和维护。
- [ ] 推荐包含适用前提、取舍、风险和备选路径。
- [ ] 结论能够指导 PoC、架构设计或开发排期。
